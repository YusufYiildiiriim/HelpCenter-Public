# Guid identity cutover notes

## Staged migration status

`20261017090000_PrepareGuidIdentity` is ordered after `20261016194811_AddAuditLogMenu` and before `20261017122147_GuidIdentityCutover`. It writes only migration-owned `GuidIdentityPrepare*` tables: entity Guid mappings, source/prepared row counts, identity references, FK metadata, and SQL module dependency inventory. It does not update application rows or alter existing keys, columns, indexes, triggers, defaults, or constraints. It captures database FK references and an explicit scalar-reference manifest including `RequestHistories.ActorAccountId` and polymorphic `AuditLogs.TargetId`. Unknown or empty identifiers, unresolved references, unclassified numeric `*Id` columns/modules, and unknown non-null audit target types fail the migration transaction.

The prepared mapping is a point-in-time snapshot. Put the application in maintenance mode and freeze all writes before Prepare; keep the freeze through Validate, Finalize, and rollback decision. Prepare and Validate acquire `TABLOCKX,HOLDLOCK` on all 30 converted tables in ascending table-name order and retain locks until their migration transaction ends. Finalize must take the same locks, in the same order, before reading any rows; hold them through exact row-by-row identity/reference parity checks and every schema change. The database application lock coordinates cooperating finalizers only; it does not stop ordinary writers, so the operational maintenance freeze remains mandatory. Plan outage duration to include full-table staging scans, validation, cutover, postcondition checks, and rollback margin. Test lock acquisition/deadlock behavior on a restored production-like database before scheduling.

`20261017100000_ValidateGuidIdentity` checks current entity rows/IDs/PublicIds, every declared numeric and text identity reference, polymorphic audit targets, and the full FK inventory against the prepared snapshot. It records a singleton gate with database name, catalog fingerprint, prepared counts, and a prepared-data summary fingerprint. `CHECKSUM_AGG(BINARY_CHECKSUM(...))` is only a compact summary and can collide; it is never proof of parity. Any snapshot drift fails Validate without changing application rows. The gate is evidence of a point-in-time check, not permission to cut over later. The retained finalizer must acquire an exclusive database application lock, keep application writes frozen, acquire the ordered table locks, and perform exact bidirectional row-by-row joins for every identity and reference under those locks. If counts, keys, values, schema, or module inventory differ, it must abort before the first drop.

Prepare inventories SQL views, procedures, functions, and triggers through catalog dependencies and conservative SQL-text matching; Validate compares that inventory and its definition hashes. The explicit `RewriteForGuid` set is `Sp_StatusDistribution`, `Sp_ModuleDistribution`, `Sp_CompanyTopN`, `Sp_AgentPerformance`, `Sp_DailyTrend`, `Sp_AvgResolutionMinutes`, `Sp_ReopenStats`, `Sp_CompletedRequests`, `Sp_ActiveRequests`, and `Sp_DashboardStats`. Finalize must recreate/verify these for Guid columns and values; in particular distribution procedure ID outputs (`StatusId`, `ModuleId`, `CompanyId`, `UserId`) must be `uniqueidentifier`, and status predicates/history comparisons must use the mapped Guid values. The explicit `PreserveUnchanged` set is `Sp_TotalRequest`, `Sp_TotalMessages`, `Sp_TotalCustomers`, `Sp_TotalCompanies`, and `TR_AuditLogs_AppendOnly`; the count procedures do not consume IDs, and the trigger only enforces append-only behavior. Any other SQL module dependency fails closed until it is explicitly classified. Finalize must preserve the append-only trigger definition, parent, UPDATE/DELETE events, enabled state, and `NOT FOR REPLICATION` state through the transaction.

`is_not_for_replication` is part of FK inventory and must be preserved when each FK is rebuilt. Finalize's postcondition, checked before commit under the same locks, is that there is no `int`/`bigint` column named `Id` or ending in `Id` in any converted table, no FK points to a removed numeric identity, no SQL module references a dropped identity, and no `GuidIdentityPrepare*` or `GuidIdentityValidateGate` object remains. This query must run against `sys.tables`, `sys.columns`, and `sys.types`; any matching row aborts the transaction. Finalize must remove the temporary numeric mapping tables only after all exact parity and postcondition checks pass.

Repository evidence: the source branch contains the cutover locally and the only references found are generic EF migration commands and the integration-test migration runner. The existing runbook says no SQL Server was migrated or rehearsed; source status is local and unpushed. Repository inspection cannot prove external database history. Confirm no external application before changing the retained migration implementation.

The `20261017122147_GuidIdentityCutover` migration uses a SQL Server shadow-column cutover. Review it against a restored production-like database before treating it as deployable.

## Migration behavior

- The manifest explicitly covers all 30 persisted entity tables: 28 `BaseEntity` tables plus `AuditLogs` and `RefreshTokens`.
- `GuidIdentityMap` stores `(EntityName, LegacyId) -> NewId` and each row's prior `PublicId`. `BaseEntity` rows reuse the existing `PublicId`; statuses 1–4 are the canonical-ID exception. A known legacy system-seed key may use its fixed seed Guid only when its legacy `PublicId` is empty. Any other empty `PublicId`, missing table, unsupported index/FK shape, duplicate map value, or unresolved reference stops the migration before key swap.
- FK/scalar columns are shadowed and mapped before legacy identity columns are dropped. Catalog metadata is recorded for primary keys, single-column identity FKs, and rowstore indexes so those definitions can be recreated on Guid columns.
- The append-only audit trigger is disabled only for the migration transaction and re-enabled after the swap. Status-dependent stored procedures are recreated with canonical status Guids; status-change history strings are converted.
- The migration keeps the identity map and captured schema metadata after cutover. Runtime system-default seeding uses the map to find migrated rows and preserve administrator and permission edits.

## Rollback

`Down` fails immediately. It does not convert rows back to numeric keys. The rollback path is restoring and verifying the pre-cutover backup, then running the old application/schema. After Guid writes begin, backup restore is the only supported rollback in this implementation.

## Verification limits

`dotnet ef migrations script --idempotent` generates deployment SQL, and source-level checks can inspect it. No SQL Server database has been migrated or rehearsed in this worktree. Before cutover, validate the generated script against a restored production-like copy, record row counts and FK/index checks, rehearse backup restore, and review the schema manifest against that database. Script generation alone is not enough to approve applying the migration.

## Seed identity note

Existing SystemDefaults rows keep their migrated `PublicId`/Guid identity and administrator edits. Missing rows on a new database use fixed seed Guids. Existing installations can retain different seed Guids between environments; statuses 1–4 use the same canonical IDs everywhere.
