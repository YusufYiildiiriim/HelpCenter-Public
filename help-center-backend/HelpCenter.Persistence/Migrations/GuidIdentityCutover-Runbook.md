# Guid identity cutover notes

## Staged migration status

Minimum supported engine: SQL Server 2019 (15.x). Prepare and Validate reject older versions before acquiring table locks. The retained cutover reads `sys.indexes.optimize_for_sequential_key`; its SQL module definitions use `CREATE OR ALTER`. Rehearse against the same SQL Server major version and compatibility level as the target.

`20261017090000_PrepareGuidIdentity` is ordered after `20261016194811_AddAuditLogMenu` and before `20261017122147_GuidIdentityCutover`. It writes only migration-owned `GuidIdentityPrepare*` tables: entity Guid mappings, source/prepared row counts, identity references, FK metadata, and SQL module dependency inventory. It does not update application rows or alter existing keys, columns, indexes, triggers, defaults, or constraints. It captures database FK references and an explicit scalar-reference manifest including `RequestHistories.ActorAccountId` and polymorphic `AuditLogs.TargetId`. Unknown or empty identifiers, unresolved references, unclassified numeric `*Id` columns/modules, and unknown non-null audit target types fail the migration transaction.

The prepared mapping is a point-in-time snapshot. Put the application in maintenance mode and freeze all writes before Prepare; keep the freeze through Validate, Finalize, and rollback decision. Prepare and Validate acquire `TABLOCKX,HOLDLOCK` on all 30 converted tables in ascending table-name order and retain locks until their migration transaction ends. Finalize acquires an exclusive transaction-owned `sp_getapplock`, then takes the same table locks in the same order before reading any rows. It holds them through exact row-by-row identity/reference parity checks, every schema change, and postcondition cleanup. The application lock coordinates cooperating finalizers only; it does not stop ordinary writers, so the operational maintenance freeze remains mandatory. Plan outage duration to include full-table staging scans, validation, cutover, postcondition checks, and rollback margin. Test lock acquisition/deadlock behavior on a restored production-like database before scheduling.

`20261017100000_ValidateGuidIdentity` checks current entity rows/IDs/PublicIds, every declared numeric and text identity reference, polymorphic audit targets, and the full FK inventory against the prepared snapshot. It records a singleton gate with database name, catalog fingerprint, prepared counts, and a prepared-data summary fingerprint. `CHECKSUM_AGG(BINARY_CHECKSUM(...))` is only a compact summary and can collide; it is never proof of parity. Validate also stores durable exact snapshots for the map, counts, references, text references, FKs, module inventory, and schema rows. At cutover, the finalizer compares those snapshots bidirectionally, refreshes validation under the held locks, and compares the refreshed gate to the previous gate. It then copies the validated Prepare map (it does not generate a second mapping) and performs exact bidirectional source-to-map/shadow checks for every entity and reference, plus text/audit parity, before the first drop. It captures full catalog metadata for every affected PK and index, including state, options, key/include columns, data space, and partition compression. Unsupported or disabled identity indexes, non-default PK options, and duplicate-key message suppression fail before the first drop; Postcondition compares the rebuilt PK/index inventory bidirectionally with the captured rows. The generated migration script orders the transaction-owned application lock, refresh, cutover, reporting procedure rewrites, and Postcondition; only Postcondition drops migration evidence, after validating rebuilt PKs/indexes/FKs/triggers/procedure metadata and no remaining numeric identity columns/dependencies. If counts, keys, values, schema, module, or index inventory differ, it aborts before cleanup. The transaction rolls back schema/data changes if any check fails.

Prepare inventories SQL views, procedures, functions, and triggers through catalog dependencies, case-insensitive bracketed/unbracketed table-name matching, and dynamic-SQL indicators; Validate compares object type, schema, definition hashes, and trigger state/events. Synonyms whose `base_object_name` targets a converted entity, and modules depending on them, fail closed. Any SQL CLR module (`PC`, `FS`, `FT`, `AF`, `TA`) anywhere in the target database fails closed, because catalog dependency metadata cannot prove the absence of runtime or dynamic database access. The explicit `RewriteForGuid` set is limited to `dbo` SQL procedure objects (`sys.objects.type='P'`): `Sp_StatusDistribution`, `Sp_ModuleDistribution`, `Sp_CompanyTopN`, `Sp_AgentPerformance`, `Sp_DailyTrend`, `Sp_AvgResolutionMinutes`, `Sp_ReopenStats`, `Sp_CompletedRequests`, `Sp_ActiveRequests`, and `Sp_DashboardStats`. Finalize must recreate/verify these for Guid columns and values; distribution procedure ID outputs (`StatusId`, `ModuleId`, `CompanyId`, `UserId`) must be `uniqueidentifier`, and status predicates/history comparisons must use mapped Guid values. The explicit `PreserveUnchanged` set is limited to `dbo` procedure objects (`P`) `Sp_TotalRequest`, `Sp_TotalMessages`, `Sp_TotalCustomers`, `Sp_TotalCompanies`, and `dbo.TR_AuditLogs_AppendOnly` of trigger type (`TR`). Preserve entries are accepted only when their definitions contain no `Id` token and no dynamic SQL; Prepare hashes the full definition and Validate requires the same hash. Other object schemas/types and unknown dependencies fail closed. Finalize must preserve the append-only trigger definition, parent, UPDATE/DELETE events, enabled state, and `NOT FOR REPLICATION` state through the transaction.

`is_not_for_replication` is part of FK inventory and must be preserved when each FK is rebuilt. Finalize's postcondition, checked before commit under the same locks, is that there is no numeric system or alias-type column named `Id` or ending in `Id` in any converted table, no FK points to a removed numeric identity, no SQL module references a dropped identity, and no `GuidIdentityPrepare*` or `GuidIdentityValidateGate` object remains. The finalizer must classify all SQL Server numeric system types by `system_type_id` (including alias types and `sql_variant` type ID 98 fail-closed); any matching row aborts. Finalize must remove temporary numeric mapping tables only after all exact parity and postcondition checks pass.

Repository evidence: the cutover source was local and unpushed, and the user confirmed it has never been applied to any database. The retained migration implementation was therefore refactored in place without changing its migration ID; all historical migration files remain. No SQL Server has been migrated or rehearsed by this work. Repository inspection cannot prove external database history beyond the user's confirmation.

## Migration behavior

- The manifest explicitly covers all 30 persisted entity tables: 28 `BaseEntity` tables plus `AuditLogs` and `RefreshTokens`.
- `GuidIdentityPrepareMap` stores a temporary `(EntityName, LegacyId) -> GuidId` mapping and each row's prior `PublicId`. `BaseEntity` rows reuse the existing `PublicId`; statuses 1–4 are the canonical-ID exception. A known legacy system-seed key may use its fixed seed Guid only when its legacy `PublicId` is empty. Any other empty `PublicId`, missing table, unsupported index/FK shape, duplicate map value, or unresolved reference stops the migration before key swap.
- FK/scalar columns are shadowed and mapped before legacy identity columns are dropped. Catalog metadata is recorded for primary keys, single-column identity FKs, and rowstore indexes so those definitions can be recreated on Guid columns.
- The append-only audit trigger is disabled only for the migration transaction and re-enabled after the swap. Status-dependent stored procedures are recreated with canonical status Guids; status-change history strings are converted.
- The final state drops temporary numeric identity maps and gate metadata after exact parity checks; runtime code must not query the migration map. System-default seeding matches existing rows by natural keys and remaps dependent seed references to the matched row IDs, preserving customized rows without a runtime migration-map dependency.

## Rollback

`Down` fails immediately. It does not convert rows back to numeric keys. The rollback path is restoring and verifying the pre-cutover backup, then running the old application/schema. After Guid writes begin, backup restore is the only supported rollback in this implementation.

## Verification limits

`dotnet ef migrations script --idempotent` generates deployment SQL, and source-level checks can inspect it. No SQL Server database has been migrated or rehearsed in this worktree. Before cutover, validate the generated script against a restored production-like copy, record row counts and FK/index checks, rehearse backup restore, and review the schema manifest against that database. Script generation alone is not enough to approve applying the migration.

## Seed identity note

Existing SystemDefaults rows keep their migrated `PublicId`/Guid identity and administrator edits. Missing rows on a new database use fixed seed Guids. Existing installations can retain different seed Guids between environments; statuses 1–4 use the same canonical IDs everywhere.
